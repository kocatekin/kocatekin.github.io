    Unit Testing I

    Today you’ll learn to write small pieces of code whose only job is to check your other code. You press one button, and in a second you know whether your program still works.

    1Why test?

    Here is a method from an online shop. It takes a price and a discount percentage and returns the new price. Read it carefully. Does it work?

    public static double priceAfterDiscount(double price, int percent) {
    return price * (1 - percent / 100);
}

    It looks fine. Most people say yes. Let’s check it the way a test would: call it with a known input, and compare the result with what we expect.

    Try it: run some checks

    Click each check. Which ones would you have tried first by hand?

    CallExpectedActualResult

    The bug is on one line: percent / 100. Both numbers are int, so Java does integer division (remember Week 1). 20 / 100 is 0, not 0.2. So the price never changes, except when the discount is exactly 100%.

    public static double priceAfterDiscount(double price, int percent) {
    return price * (1 - percent / 100.0);   // 100.0 makes it double division
}

    Notice something important: the two checks most people try first, 0% and 100%, both passed. The bug was hiding in the middle.

    Checking by hand doesn’t scale

    You could test everything by hand with a main method and System.out.println. The problem is that you have to read the output and decide yourself if it’s right, and you have to do it again every time you change the code. Nobody does that for 200 methods.

    A unit test is a small method that calls your code with a known input and checks the output automatically. If the answer is wrong, it fails loudly and tells you what it expected and what it got. That gives you three things:

    • Bugs are found early, while you still remember the code, instead of by a customer.
    • You can change code without fear. If you break something, a test turns red within seconds.
    • Tests explain the code. A test named twentyPercentOff shows exactly how the method should behave.

    2Same object or equal object?

    Before we write tests, we need one idea that tests depend on: what does it mean for two objects to be “equal”? Java has two different answers.

    Point a = new Point(1, 2);
Point b = new Point(1, 2);
Point c = a;

    Three variables, but how many objects? Only two. Every new creates one object in memory. c = a does not copy the object; it copies the arrow (the reference), so a and c point to the same object.

    Try it: compare the variables

    Click an expression to see what Java compares. Then flip the switch and try .equals() again.

    Point class:

    The rule to remember:

    • == on objects asks: is it the same object? (Do both arrows point to the same place?)
    • .equals() asks: do they have the same value? But only if the class tells Java what “same value” means.

    If you don’t override equals(), your class inherits it from Object, and Object.equals() just does ==. That’s why a.equals(b) was false until you flipped the switch. For primitives like int and double, == compares values, which is what you want.

    Writing equals() for Point

    public class Point {
    private int x;
    private int y;

    public Point(int x, int y) { this.x = x; this.y = y; }

    @Override
    public boolean equals(Object other) {
        if (this == other) return true;                       // same object
        if (other == null || getClass() != other.getClass()) return false;
        Point p = (Point) other;                              // cast (Week 3!)
        return x == p.x && y == p.y;                        // same values
    }

    @Override
    public int hashCode() {
        return Objects.hash(x, y);    // we'll see why in a minute
    }

    @Override
    public String toString() {
        return "Point(" + x + ", " + y + ")";
    }
}

    You rarely type this by hand. In IntelliJ: right-click inside the class, choose Generate, then equals() and hashCode().

    Predict the answer before you click.

    Why tests care: assertEquals uses equals()

    The most common test check is assertEquals(expected, actual). Behind the scenes it calls expected.equals(actual). So if your class has no equals(), a test comparing two objects will fail even when the values are identical.

    @Test
void moveRightAddsOneToX() {
    Point p = new Point(1, 2);
    p.moveRight();
    assertEquals(new Point(2, 2), p);
}

    Try it: run this test

    moveRight() works correctly in both cases. Only the Point class changes.

    The partner rule: hashCode()

    HashSet and HashMap don’t search every element. They first compute a number from the object, called its hash code, and use it to pick a bucket. Then they look only inside that bucket and use equals() there. If two equal objects produce different hash codes, Java looks in the wrong bucket and never finds a match.

    Set<Point> set = new HashSet<>();
set.add(new Point(1, 2));
boolean found = set.contains(new Point(1, 2));   // true or false?

    Try it: watch the HashSet

    Pick what the Point class overrides, then run. Watch which bucket Java looks in. (Simplified: a real HashSet has more buckets.)

      The rule

      If you override equals(), always override hashCode() too. Equal objects must have equal hash codes. And override toString() so failing tests print something readable.

      4Arrange, Act, Assert

      Almost every good test has the same three parts, in the same order. If you remember one thing about writing tests, remember this.

      ArrangeSet up the objects and data you need.
      ActCall the one method you are testing.
      AssertCheck that the result is what you expected.

      Think of a science experiment: prepare the equipment (arrange), do the experiment (act), write down whether it matched your prediction (assert).

      Try it: label each line

      We are testing withdraw(). Click a label to cycle through Arrange, Act, Assert. Then check.

      One test, one behaviour

      A common beginner mistake is to test many things in one long method: act, assert, act again, assert again. When it fails, you don’t know which part broke, and everything after the first failure never runs.

      Compare

      @Test
void testAccount() {
    BankAccount account = new BankAccount("Ali");
    account.deposit(100);
    assertEquals(100, account.getBalance());
    account.withdraw(30);
    assertEquals(70, account.getBalance());
    account.withdraw(500);                      // what should happen here?
    assertEquals(70, account.getBalance());
}
      @Test
void depositIncreasesBalance() {
    BankAccount account = new BankAccount("Ali");

    account.deposit(100);

    assertEquals(100, account.getBalance());
}

@Test
void withdrawReducesBalance() {
    BankAccount account = new BankAccount("Ali");
    account.deposit(100);

    account.withdraw(30);

    assertEquals(70, account.getBalance());
}

      The name testAccount tells you nothing. If the first assert fails, the other checks never run.

      Naming tests

      Name the test after the behaviour, as a short sentence: withdrawReducesBalance, emptyCartHasZeroTotal, negativeAgeIsRejected. When it fails, the name alone tells you what’s broken. A blank line between the three parts makes the structure easy to see.

      5The assertion toolbox

      An assertion is the check at the end of a test. If it’s true, nothing happens. If it’s false, the test stops and fails with a message. They all live in org.junit.jupiter.api.Assertions.

      AssertionUse it when
      assertEquals(expected, actual)You know the exact value. The one you’ll use most.
      assertTrue(condition)The result is a boolean that should be true.
      assertFalse(condition)The result is a boolean that should be false.
      assertNull(object)Something should be missing, for example “not found”.
      assertNotNull(object)Something should exist, but you don’t care about its exact value.
      assertEquals(e, a, delta)Comparing double values. Allows a tiny difference.
      assertThrows(Type.class, () -> ...)The code should throw an exception.

      Expected first, actual second

      assertEquals takes the expected value first. Java can’t check that you got the order right, but the failure message will be backwards and confusing if you swap them.

      Try it: read the failure message

      There’s a bug: the balance is 60 instead of 70. Which message makes it obvious?

      Doubles are not exact

      Computers store double values in binary, and some decimals can’t be stored exactly, like 1/3 in decimal. So never compare doubles with plain assertEquals(expected, actual).

      Testing exceptions: assertThrows

      Last week you made methods throw exceptions when something is wrong. A test should check that too. assertThrows runs a piece of code and passes only if the right exception is thrown.

      @Test
void withdrawingTooMuchThrows() {
    // Arrange
    BankAccount account = new BankAccount("Ali");
    account.deposit(50);
    // Act + Assert
    InsufficientFundsException ex = assertThrows(
            InsufficientFundsException.class,
            () -> account.withdraw(80)
    );
    assertEquals("Balance is 50, cannot withdraw 80", ex.getMessage());
}

      The new part is () -> account.withdraw(80). Read it as “here is a piece of code; JUnit, please run it for me.” We can’t just call account.withdraw(80) directly, because the exception would crash the test before assertThrows could catch it. assertThrows also gives you the exception back, so you can check its message.

      Check yourself: pick the best assertion

      6Choosing test inputs

      You can’t test every possible input. The grade method below accepts any int, that’s over four billion values. So which few should you test?

      public static char grade(int score) {
    if (score < 0 || score > 100) {
        throw new IllegalArgumentException("score must be 0-100");
    }
    if (score >= 90) return 'A';
    if (score >= 80) return 'B';
    if (score >= 70) return 'C';
    if (score >= 60) return 'D';
    return 'F';
}

      Two simple ideas help:

      • Groups. Split the inputs into groups that should behave the same way. 72 and 75 are both a C, so testing both doesn’t teach you much. Here there are 7 groups: too low, F, D, C, B, A, too high.
      • Edges. Bugs love edges. Programmers write > when they meant >=. So test the values right at each edge: 89 and 90, 59 and 60, -1 and 0, 100 and 101.

      7Unit vs integration tests

      A unit test checks one small piece, usually one method of one class, on its own. It needs nothing outside your code: no database, no internet, no files. So it runs in milliseconds.

      An integration test checks that several pieces work together: your code plus a real database, or your code calling a real web service. These catch different bugs, for example a wrong SQL query, but they are slower and can fail for reasons that aren’t your code’s fault, like the Wi-Fi going down.

      This is the test pyramid. Most of your tests should be unit tests at the wide bottom: fast, many, and precise about what broke. Fewer integration tests sit in the middle. At the top are a handful of end-to-end tests that click through the whole app like a user.

      This course focuses on the bottom layer.

      Try it: sort the tests

      Is each one a unit test or an integration test?

      What makes a good unit test

      A useful checklist is FIRST. Good unit tests are Fast (milliseconds), Independent (no test depends on another test running first), Repeatable (same result every time, on every computer), Self-checking (pass or fail on their own, no human reading output), and Timely (written while you write the code, not months later).

      8Code that is easy to test

      Some code is easy to test and some code fights you. Here is a class that sends a greeting to a student. Try to imagine writing a test for it.

      public class BirthdayGreeter {
    public void greet(Student s) {
        LocalDate today = LocalDate.now();
        if (s.getBirthday().getMonth() == today.getMonth()
                && s.getBirthday().getDayOfMonth() == today.getDayOfMonth()) {
            System.out.println("Happy birthday, " + s.getName() + "!");
        } else {
            System.out.println("Hello, " + s.getName());
        }
    }
}
      public class BirthdayGreeter {
    public String greeting(Student s, LocalDate today) {
        boolean birthday = s.getBirthday().getMonth() == today.getMonth()
                && s.getBirthday().getDayOfMonth() == today.getDayOfMonth();
        return birthday ? "Happy birthday, " + s.getName() + "!"
                        : "Hello, " + s.getName();
    }
}

      The red lines are problems. Open each one:

      It secretly asks the calendar for today’s date

      LocalDate.now() is a hidden input. A test that checks the birthday message passes only on the student’s birthday and fails the other 364 days. A test whose result changes depending on when you run it is called flaky, and nobody trusts it.

      It prints instead of returning

      System.out.println sends the text to the screen. A test can’t easily grab it, so there’s nothing to give to assertEquals. A method that returns a value is much easier to check.

      It does two jobs at once

      It decides what to say and it delivers the message. Those are two reasons to change. Keep the decision separate and you can test it on its own. (You’ll meet this idea again in Week 9 as the Single Responsibility Principle.)

      The fix: pass the date in as a parameter, and return the text instead of printing it. Some other code can do the printing. Now the test controls every input:

      @Test
void birthdayStudentGetsBirthdayGreeting() {
    Student ayse = new Student("Ayşe", LocalDate.of(2005, 3, 14));
    BirthdayGreeter greeter = new BirthdayGreeter();

    String text = greeter.greeting(ayse, LocalDate.of(2026, 3, 14));

    assertEquals("Happy birthday, Ayşe!", text);
}

      Try it: run the birthday test on different days

      Ayşe’s birthday is 14 March. Pretend the test suite runs on each of these days. (For the Before version, imagine we somehow captured what it printed.)

      Warning signs of hard-to-test code

      • Hidden inputs: LocalDate.now(), Math.random(), reading from the keyboard. Fix: pass the value in.
      • Results that are printed instead of returned. Fix: return the value; print somewhere else.
      • A method that creates heavy things itself, like new DatabaseConnection(). Fix: pass the object in. This is the big topic of Week 8, where we’ll replace real databases with fake ones in tests.
      • One giant method doing many jobs. Fix: split it into smaller methods you can test one by one.

      Notice the pattern: code that is easy to test is usually also code that is well designed. Testing is a good way to discover design problems early.

      9Bug hunt

      Time to read tests like a professional. Below is a test class for a ShoppingCart. Three students each wrote a ShoppingCart, and each version has one bug. You won’t see their code. Run the tests, read the failure, and figure out the bug from the test results alone.

      class ShoppingCartTest {

    @Test
    void emptyCartHasZeroTotal() {
        ShoppingCart cart = new ShoppingCart();
        assertEquals(0.0, cart.total(), 0.001);
    }

    @Test
    void totalMultipliesPriceByQuantity() {
        ShoppingCart cart = new ShoppingCart();
        cart.add("Pen", 5.0, 2);
        cart.add("Book", 20.0, 1);
        assertEquals(30.0, cart.total(), 0.001);
    }

    @Test
    void itemCountCountsEveryPiece() {
        ShoppingCart cart = new ShoppingCart();
        cart.add("Pen", 5.0, 2);
        cart.add("Book", 20.0, 1);
        assertEquals(3, cart.itemCount());
    }

    @Test
    void removeTakesTheItemOut() {
        ShoppingCart cart = new ShoppingCart();
        cart.add("Pen", 5.0, 2);
        cart.remove("Pen");
        assertEquals(0, cart.itemCount());
    }

    @Test
    void negativeQuantityIsRejected() {
        ShoppingCart cart = new ShoppingCart();
        assertThrows(IllegalArgumentException.class,
                     () -> cart.add("Pen", 5.0, -1));
    }
}

      Test template

      import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class ThingTest {

    @Test
    void behaviourInPlainWords() {
        // Arrange
        Thing thing = new Thing();

        // Act
        int result = thing.doSomething(42);

        // Assert
        assertEquals(84, result);
    }
}

      Assertions

      assertEquals(expected, actual)Exact value. Objects need equals().
      assertEquals(e, a, 0.0001)For double values.
      assertTrue(x) / assertFalse(x)For booleans.
      assertNull(x) / assertNotNull(x)Missing or present.
      assertThrows(E.class, () -> code)The code must throw E. Returns the exception.

      Remember

      • == means same object; .equals() means same value. Override equals(), hashCode() and toString() together.
      • One behaviour per test, named as a sentence.
      • Test each group of inputs once, and test both sides of every edge.
      • Pass hidden inputs (dates, random numbers) in as parameters. Return values instead of printing.
