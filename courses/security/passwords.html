Passwords

How strong a password really is, how servers should store it, how attackers break it, and what we add on top of it (password managers, MFA, passkeys). Every box marked INTERACTIVE runs entirely in your browser — nothing leaves this page.

01 · Measuring strength

Entropy

Entropy measures how unpredictable something is. For passwords it answers: how many guesses would an attacker need? It is measured in bits: if something can take N equally likely values, its entropy is log₂(N) bits. Every extra bit doubles the attacker's work.

Careful — a common mistake A passphrase of 5 random words (~25 letters) is not 26²⁵ ≈ 117 bits. The attacker doesn't guess letter by letter; they guess words from the list. The unit of randomness is the word, so the right count is (list size)words: 7776⁵ ≈ 264.6. Always compute entropy over the process that generated the password, not over its characters.
The formula only works for random passwords L·log₂S assumes every character was picked uniformly at random by a machine or dice. Humans don't do that. Password1! "uses" 95 symbols × 10 chars = 65.7 bits on paper, but it is among the first few thousand guesses of any cracker. For human-chosen passwords, use a pattern-aware estimator instead.

How many bits do we need?

It depends on the threat model — how fast the attacker can guess:

  • Online attack (guessing through the login page, rate-limited): ~30–40 bits is plenty, because the server only lets you try a few guesses per minute.
  • Offline attack (the attacker stole the hash database and guesses on their own GPUs): aim for ≥ 70–80 bits. A slow password hash (Argon2, bcrypt…) buys you ~10–20 bits of "free" margin, a fast hash (MD5, SHA-1) buys you nothing.
  • Cryptographic keys: 128 bits or more.
02 · Users' side

Choosing a password

  • Length beats complexity. Each extra character multiplies the search space by S; adding one symbol class only grows S a little. 16 lowercase letters (75 bits) beat 8 characters from all of ASCII (53 bits).
  • Never reuse passwords. When one site is breached, attackers try the same email/password on every other site (credential stuffing). They don't even need to crack anything if the site stored it badly.
  • Hard for humans ≠ hard for computers. Tr0ub4dor&3 is hard to remember but built from a dictionary word with predictable substitutions. A random passphrase is the opposite: easy to remember, hard to guess.
  • Very long, random passwords are hard to memorise → users write them on sticky notes. The practical answers are passphrases for the few passwords you must memorise, and a password manager for everything else.

Passphrases

A passphrase is a memorised secret made of a sequence of words. It is longer than a typical password, so it reaches high entropy while staying memorable — but only if the words are chosen randomly. A famous quote or song lyric is a terrible passphrase: attackers have wordlists of those too.

Websites must therefore allow long inputs (at least 64 characters) and spaces — otherwise users simply cannot use passphrases.

Diceware

Diceware turns physical dice into a passphrase: roll 5 dice → a 5-digit number (e.g. 3-4-1-6-2 → 34162) → look it up in a list of 6⁵ = 7776 words. Each word adds log₂(7776) ≈ 12.9 bits. Dice are a true random source; no human bias sneaks in. (The EFF publishes a widely used improved list.)

03 · Feedback for users

Password strength meters

Traditional meters use simple heuristics: points for length, uppercase, digits, symbols. They reward exactly the predictable tricks attackers already know (P@ssw0rd! scores "strong").

zxcvbn (by Dropbox, 2012; the most widely used open-source meter) instead thinks like a cracker: it splits the password into patterns — dictionary words, common passwords, names, l33t substitutions, keyboard walks (qwerty), sequences (abcd, 1234), repeats, dates — and estimates the number of guesses a smart attacker would need.

04 · Rules for organisations

Password policies

A password policy is the set of rules defining how users create and manage passwords. Typical knobs: minimum/maximum length, complexity (character classes), expiration/rotation, history (no reuse of last n), MFA requirements and account lockout/throttling.

Many traditional rules turned out to hurt security. Modern guidance — NIST SP 800-63B (revision 4, 2025) and the OWASP cheat sheets — flips several of them. Click each card:

Old ruleMust contain upper, lower, digit and symbol.

Good practices (summary)

  • Enforce a reasonable minimum length; accept long passphrases (≥ 64 chars).
  • Reject passwords found in breach corpora / common-password lists (e.g. via HIBP), dictionary words, and context words (site name, username).
  • No forced rotation, no composition rules, no password hints.
  • Support password managers: standard <form> with <input type="password" autocomplete="current-password"> / "new-password", allow paste, no JavaScript tricks that hide the field.
  • Offer and encourage MFA (ideally phishing-resistant: passkeys / security keys).
  • Store passwords with a slow, salted password hash (next section).
  • Throttle online guessing; log and monitor authentication events.
Why "change every 3 months" doesn't help If the database used a strong algorithm (Argon2/bcrypt + salt) and users chose decent passwords, cracking takes far longer than 3–6 months anyway. If an attacker already has the password, they use it within minutes, not after 90 days. Meanwhile the rule pushes users toward weaker, predictable passwords.
05 · Servers' side

Storing passwords

Rule zero: never store passwords in plaintext, and never encrypt them reversibly either (whoever gets the key gets every password). Store the output of a one-way function. At login, compute the function again on what the user typed and compare.

But a plain cryptographic hash such as SHA-256(password) is not enough, for two reasons:

  1. Identical passwords → identical hashes. The attacker instantly sees which users share a password, can crack them all at once, and can use precomputed tables (lookup / rainbow tables) built once for everyone.
  2. General-purpose hashes are fast — billions per second on a GPU. Speed is great for checking file integrity and terrible for passwords.

The fixes: a salt (solves 1), a pepper (extra layer), and a deliberately slow password-hashing function (solves 2).

Salting

  • A salt is a random value (≥ 16 bytes from a CSPRNG), unique per user (and per password change). Store hash(salt ‖ password) together with the salt.
  • The salt is not secret — it lives in the database right next to the hash. Its job is not to hide anything but to make every hash unique.
  • Effects: equal passwords no longer have equal hashes; precomputed tables become useless (one table per salt would be needed); the attacker must attack each user separately, so cracking a million users costs a million times more.
  • What salt does not do: it doesn't make guessing a single user's weak password slower. That's the job of the slow hash.

Peppering

  • A pepper is a secret value shared by all users that is not stored in the database — it lives in the application config, an environment variable, or best of all an HSM / secrets vault.
  • If only the database leaks (e.g. SQL injection, a stolen backup), the attacker cannot test a single guess without the pepper.
  • Preferred construction: HMAC(pepper, password_hash) or encrypting the stored hash with the pepper key — rather than plain concatenation hash(pw ‖ salt ‖ pepper). Peppering is defence-in-depth, never a replacement for salt + slow hash. Downside: rotating a pepper is hard.
06 · Which function?

Slow hashes & key derivation functions

A key derivation function (KDF) takes an input (a password, or other key material) and outputs a key of a chosen fixed length, to be used by another cryptographic algorithm (e.g. a 256-bit AES key). Not every KDF is slow — HKDF, for example, is fast and meant for high-entropy inputs. The ones we care about are password-based KDFs / password hashing functions, which are deliberately expensive: one guess costs the defender milliseconds once per login, but costs the attacker those milliseconds × billions of guesses.

That's why we use PBKDF2, bcrypt, scrypt or Argon2 for passwords, and not SHA-256, SHA-3, or MD5.

Interactive · Feel the cost of a slow hashPBKDF2-HMAC-SHA256 in pure JavaScript

This runs in single-threaded JavaScript (much slower than native code). The point is the ratio: 1 iteration ≈ 1 SHA-256; 600,000 iterations makes every attacker guess ~600,000× more expensive.

PBKDF2 2000 · RFC 8018

Applies a PRF (usually HMAC-SHA256) to password + salt, iterated c times; output length is selectable → it is a true KDF. Widely deployed: WPA2 Wi-Fi, iOS/macOS keychain, TrueCrypt/VeraCrypt, RAR5, many password managers.

Weakness: only CPU-hard. It needs almost no memory, so GPUs/ASICs run it massively in parallel. OWASP: ≥ 600,000 iterations with HMAC-SHA256.

bcrypt 1999

Based on the Blowfish cipher's deliberately expensive key schedule ("EksBlowfish"). Has a tunable cost factor: work = 2cost. Default in OpenBSD; very common in web frameworks.

It's a password hash, not a general KDF: its output is a fixed 184-bit value you cannot size to your needs. Uses 4 KB of memory (mildly GPU-unfriendly). Gotcha: only the first 72 bytes of the password are used. OWASP: cost ≥ 10.

Anatomy of a bcrypt hash — hover the parts

Algorithm · cost · salt · hash are all stored in one string, so the verifier knows exactly how to recompute it. Argon2 does the same: $argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>.

Why iteration count alone is not enough: memory-hard functions

We keep raising iteration counts as CPUs get faster, but attackers don't use CPUs — they use GPUs with thousands of cores, or custom ASICs/FPGAs. Computation is cheap to parallelise; memory is not. A memory-hard function forces every single guess to fill and repeatedly read a big block of RAM, so the number of parallel guesses is limited by memory, not by core count.

Interactive · Memory-hardness vs a 24 GB GPUillustrative

scrypt 2009 · RFC 7914

Designed by Colin Percival to be memory-hard: it fills a large array with pseudo-random data and then reads it in data-dependent order. Parameters: N (CPU/memory cost), r (block size), p (parallelism). Also used as proof-of-work in Litecoin and Dogecoin. OWASP: N=2¹⁷, r=8, p=1 (≈128 MiB).

Argon2 2015 · RFC 9106

Winner of the Password Hashing Competition (2015) and today's first choice. Tunable memory (m), time/iterations (t) and parallelism (p). Variants: Argon2d (data-dependent, GPU-resistant, side-channel-prone), Argon2i (data-independent), Argon2id (hybrid — use this one). OWASP minimum: m = 19 MiB, t = 2, p = 1.

Upgrading an existing database to a better algorithm

You can't recompute a new hash without the plaintext — and you only see the plaintext when a user logs in. Two strategies:

1 · Rehash on login

Mark each row with its algorithm. When a user logs in successfully with an old hash, compute the new hash from the password they just typed and replace it. Problem: inactive users keep weak hashes forever.

2 · Wrap immediately (layering)

Right now, for every row: new = Argon2id(salt₂, old_md5_hash) and delete the old hash. Verify with Argon2id(salt₂, MD5(salt₁‖pw)). On the user's next login, migrate to a clean Argon2id(pw). Every account is protected from day one.

07 · The other side

Attacks on passwords

Websites should follow the practices above — many don't. Assume your hash may be stolen someday, and choose passwords accordingly. Attacks fall into two families:

🌐 Online attacks

Guesses go through the real login page/API. Limited by network speed, rate limiting, lockouts, CAPTCHAs, monitoring. Examples: guessing, password spraying, credential stuffing.

💾 Offline attacks

The attacker stole the hash database and guesses on their own hardware — no rate limit, no alerts. Speed depends only on the hash function and their GPUs. Examples: brute force, dictionary + rules, rainbow tables.

…and attacks that skip guessing entirely by stealing the password from the human or their device: phishing, keylogging, shoulder surfing, social engineering.

Guessing & password spraying

  • Manual / targeted guessing: using personal info (birthday, pet's name, favourite team) or default credentials (admin/admin).
  • Password spraying: try one very common password against many accounts, then the next password, slowly. Each account sees only one or two failures, so per-account lockout never triggers.
Animation · Brute force on one account vs spraying manylockout after 3 failures

Credential stuffing

Attackers take username/password pairs leaked from one breach and automatically try them on other sites. It works only because people reuse passwords. Defences: unique passwords (password manager), MFA, checking logins against breached-password lists, bot detection and rate limiting by IP/device.

Animation · One leak, many doors

Phishing

Tricking the user into typing the password into a fake page (fake email + look-alike domain such as paypa1.com). The page may also proxy the real site in real time ("adversary-in-the-middle"), so it can relay a one-time code too. MFA with OTPs or push reduces the damage but can still be phished this way; only origin-bound methods — passkeys / FIDO2 security keys — are phishing-resistant. Password managers help too: they refuse to autofill on the wrong domain.

Keylogging

Software (often installed by malware) or a hardware dongle between keyboard and computer that records every keystroke — passwords included. MFA limits the damage; endpoint security and not using untrusted machines prevent it.

Social engineering & shoulder surfing

  • Social engineering: manipulating people into revealing secrets — e.g. calling an employee while pretending to be IT support, or calling the help desk pretending to be the employee. Kevin Mitnick (1963–2023), once the FBI's most-wanted hacker, got most of his access this way (see his book Ghost in the Wires).
  • Shoulder surfing: watching someone type — in a bus, café, office. Advanced variants: binoculars, hidden cameras, thermal imaging of a keypad right after use to see which keys are warm. Defences: privacy screen filters, covering the keypad, biometrics/passkeys (nothing to observe).
08 · Offline

Cracking stolen hashes

Online guessing is slow and noisy: the server will throttle or ban you. So the serious attacks are offline: steal the database first, then guess locally. Tools: hashcat (GPU) and John the Ripper (CPU/GPU). Both parallelise across many GPUs, and hardware gets faster every year — which is why stored-hash parameters must keep growing.

The loop is always the same: for guess in candidates: if H(salt, guess) == stolen_hash: found!. What differs is where the candidates come from.

Brute force

Try every possible string: aaaa, aaab, aaac, …. Guaranteed to succeed eventually; the time is SL / speed (on average half of that). Length dominates: each additional character multiplies the time by S.

Wordlists are then expanded with mangling rules that mimic how people "strengthen" words: capitalise, append digits/years, l33t-speak, reverse, duplicate. hashcat ships rule files (e.g. best64.rule) and you can write your own.

Lookup tables & rainbow tables

Because a hash function is deterministic, an attacker can compute hashes once, in advance, and reuse the work against every unsalted database:

  • Lookup table: store every (hash → password) pair. Instant lookup, but enormous storage.
  • Rainbow table: a time–memory trade-off. Build chains p₀ → H → R₁ → p₁ → H → R₂ → … using reduction functions R that map a hash back to some candidate password, and store only the first and last element of each chain. To crack a hash, apply R/H steps until you hit a stored endpoint, then regenerate that chain from its start.
Animation · Building one rainbow-table chain
DefenceA unique random salt per user defeats both: a precomputed table would have to be rebuilt for every salt value, which is no better than attacking each hash directly.
09 · Building it right

Login responses, password recovery & logging

Authentication responses: don't leak information

If the login page answers differently for "this user doesn't exist" and "wrong password", an attacker can enumerate valid accounts and then focus guessing (or phishing) on them. Messages to avoid: "Wrong password for user", "Invalid user ID", "Account disabled", "User not active". Use one generic message: "Login failed: invalid username or password."

The same applies to registration and password reset pages, and to response time: if the server skips the slow hash for unknown users, the faster response leaks the same information. Run a dummy hash so both paths take equal time.

Password recovery

Red flagA site that can email you your current password stores it in plaintext or reversibly encrypted. Leave — and make sure that password isn't used anywhere else.

The correct mechanism is a reset link containing a secure, single-use, time-limited token:

Step-through · Secure password-reset flow

Token requirements: generated by a CSPRNG; long (≥ 128 bits) and unique; stored hashed in the DB (a DB leak must not give working reset links); short expiry (e.g. 15–60 min) and deleted when expired; single-use; invalidated when a new one is requested. After a successful reset: invalidate existing sessions, notify the user by email, and don't log the user in automatically if MFA is enabled.

Rate limiting, lockout & logging

  • Throttle failed attempts per account and per IP/device (exponential back-off, CAPTCHA after a few failures). Use temporary, not permanent, lockouts to avoid enabling denial-of-service.
  • Log every authentication event: successes, failures, lockouts, password changes and resets, MFA changes — with timestamp, account, source IP, user agent. Review them and alert on anomalies (spraying patterns, logins from new countries, impossible travel).
  • Never log passwords — not even failed ones. Users often type their password into the username field by mistake, so be careful logging failed usernames too.
  • Compare hashes with a constant-time comparison function.
10 · Breach checking

Have I Been Pwned & k-anonymity

haveibeenpwned.com (Troy Hunt) aggregates public data breaches. You can check whether your email appears in a breach, and the separate Pwned Passwords service holds hundreds of millions of leaked passwords that sites can use to reject breached passwords at sign-up.

But sending your password (or even its full hash) to a third party would be a bad idea. Pwned Passwords uses k-anonymity via a range query:

  1. Locally compute SHA-1(password) → 40 hex chars.
  2. Send only the first 5 hex chars (the prefix) to https://api.pwnedpasswords.com/range/<prefix>.
  3. The server returns all suffixes (the other 35 chars) of known breached hashes sharing that prefix — typically ~800–1000 of them — each with a breach count.
  4. Your machine checks locally whether your suffix is in the list.

The server only learns that your hash is one of ~1000 with that prefix (16⁵ ≈ 1 M possible prefixes) — it never learns your password or which hash you were interested in. (An optional Add-Padding header also hides the response size.)

Interactive · k-anonymity range querysimulated server (works offline)
Python code (real API) 
import hashlib, requests

def pwned_count(password: str) -> int:
    sha1 = hashlib.sha1(password.encode("utf-8")).hexdigest().upper()
    prefix, suffix = sha1[:5], sha1[5:]
    r = requests.get(f"https://api.pwnedpasswords.com/range/{prefix}",
                     headers={"Add-Padding": "true"}, timeout=10)
    r.raise_for_status()
    for line in r.text.splitlines():
        h, count = line.split(":")
        if h == suffix:
            return int(count)          # padded entries have count 0
    return 0

for pw in ["password123", "correct horse battery staple"]:
    n = pwned_count(pw)
    print(f"{pw!r}: " + (f"seen {n:,} times in breaches!" if n else "not found"))

SHA-1 is used here only as an identifier for lookups — not for storing passwords. Its collision weaknesses don't matter for this purpose.

11 · Tools

Password managers

Programs, browser extensions or services that store all your credentials in an encrypted vault. You memorise one strong master password (a good passphrase); the manager generates unique random passwords for every site, fills them in automatically, and syncs across devices. Autofill also protects against phishing: it won't fill paypa1.com with your PayPal password.

They can have implementation bugs and are a high-value target, so no manager is "100% secure" — but using one is far safer than reusing passwords. Questions to ask about any manager: Where does encryption happen? Which cipher? How is the key derived? What is stored unencrypted? Read its security whitepaper.

Zero-knowledge design: where is the key?

Obviously not in the database. The vault key is derived from the master password with a password-based KDF, on the client. The server only receives the encrypted vault and a separate authentication hash — never the master password or the vault key.

Animation · How a zero-knowledge manager derives keys

Case study: LastPass

  • Local-only encryption: encryption/decryption happens on the user's device; the vault is synced to LastPass servers as an encrypted (base64-encoded) blob. LastPass doesn't hold the master password or key.
  • Vault key: PBKDF2-HMAC-SHA256(master password, salt = username/email, iterations) → used with AES-256.
  • Login: one more PBKDF2 round over (key, master password) gives the authentication hash, which is sent to the server; the server hashes it again with a random salt and 100,000 more PBKDF2 rounds before storing and comparing.
  • The default client iteration count changed over time: 5,000 → 100,100 (2018) → 600,000 (2023).
Lesson from the 2022 LastPass breach Attackers stole encrypted vault backups. The zero-knowledge design meant they still had to crack master passwords offline — but (1) old accounts that were never migrated still had very low iteration counts (some as low as 5,000 or even 1), (2) website URLs were stored unencrypted, telling attackers which vaults were worth cracking (e.g. crypto-wallet users), and (3) weak master passwords fell quickly. Takeaways: design is only as strong as its parameters for every user, encrypt metadata too, and keep the master password strong.
12 · Beyond passwords

Multi-factor authentication (MFA)

An authentication factor is a category of evidence that you are who you claim to be:

🧠 Something you know

password, PIN, passphrase

📱 Something you have

phone with authenticator app, hardware security key (YubiKey), smart card

🫆 Something you are

fingerprint, face, iris, voice (biometrics)

MFA requires factors from at least two different categories. A password plus a security question is still single-factor (both are "know"). Even if your password is stolen, the attacker also needs your device or your finger.

13 · One-time passwords

HOTP & TOTP

A one-time password (OTP) is a code valid for a single use or a short time. Both device and server share a secret key K and compute the same code independently. Benefits: a captured code is useless later (protects against replay), limited validity, and nothing guessable.

HOTP — HMAC-based (RFC 4226)

Moving factor = an event counter C that increments each time a code is generated. Works offline; good for hardware tokens (e.g. YubiKey OATH-HOTP, bank tokens). Codes stay valid until used.

TOTP — Time-based (RFC 6238)

Moving factor = time step T = ⌊(unix time − T₀) / 30⌋. A new code every 30 s whether you ask or not. Used by Google Authenticator, Microsoft Authenticator, Authy…

The HOTP algorithm

HS   = HMAC-SHA-1(K, C)                 // 20 bytes; C is an 8-byte big-endian counter
off  = HS[19] & 0x0F                     // "dynamic truncation": low 4 bits of last byte
bin  = (HS[off] & 0x7F)‖HS[off+1]‖HS[off+2]‖HS[off+3]   // 31-bit integer
HOTP = bin mod 10^6                      // 6 digits
TOTP = HOTP(K, T)                        // same thing, with the time step as counter

What if I press the button twice by mistake? The device counter is now ahead of the server's. The server therefore checks a look-ahead window: C, C+1, …, C+w. If a code matches at C+k, the server resynchronises its counter to C+k+1 (so the code can't be reused). If you press more than w times without logging in, the token is out of sync and must be resynchronised (e.g. by entering two consecutive codes). A bigger window is more forgiving but gives an online guesser more valid codes per attempt — so throttle attempts.

Because phone and server clocks drift and users need time to type, servers usually accept the codes for T−1, T, T+1. A good server also remembers the last accepted T per user and rejects a second use of the same code (otherwise a code could be replayed within its 30-second window).

How is the shared secret shared?

During 2FA enrolment the server generates a random secret (≥ 128 bits, typically 160) and shows it as a QR code encoding a URI such as:

otpauth://totp/Arel%20CS:ayse@arel.edu.tr?secret=GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ&issuer=Arel%20CS&algorithm=SHA1&digits=6&period=30

The authenticator app scans it, stores the secret, and from then on both sides compute the same codes. Consequences: that QR code is as sensitive as a password (show it once, over HTTPS); the server must keep secrets retrievable (it needs K to compute codes), so it should store them encrypted, not hashed; and the user should get backup/recovery codes.

14 · The future

Passkeys (FIDO2 / WebAuthn)

Passkeys replace the shared secret with a public/private key pair per website:

  1. Registration: the device creates a key pair for this exact origin (e.g. arel.edu.tr). The public key goes to the server; the private key never leaves the device / secure hardware (or is synced end-to-end encrypted by the platform).
  2. Login: server sends a random challenge; the device asks for a fingerprint/face/PIN locally, then signs the challenge together with the origin. Server verifies with the public key.

No shared secret

A server breach leaks only public keys — useless to an attacker. Nothing to crack.

Phishing-resistant

The browser includes the real origin; a key for arel.edu.tr will never sign for arel-edu.tr.login.xyz.

Two factors in one

Have (the device) + are/know (biometric or PIN to unlock it). Nothing to type, nothing to shoulder-surf.

15 · Check yourself

Quiz

One-page summary

Users

  • Length > complexity; entropy of random passwords = L·log₂S
  • Random passphrases (Diceware: 12.9 bits/word)
  • Never reuse → password manager
  • Turn on MFA; prefer passkeys/security keys

Developers

  • Argon2id (or scrypt/bcrypt/PBKDF2) + unique salt; optional pepper
  • Min length, allow ≥64 chars & paste, blocklist breached passwords, no rotation/composition rules
  • Generic login errors, equal timing
  • Reset via hashed, single-use, expiring CSPRNG tokens
  • Throttle, log, monitor — never log passwords

Attacks

  • Online: guessing, spraying, stuffing
  • Offline: brute force, dictionary + rules, rainbow tables (beaten by salt)
  • Steal it: phishing, keylogging, shoulder surfing, social engineering

MFA

  • Know / have / are — two different categories
  • HOTP: HMAC-SHA1(K, counter), look-ahead window
  • TOTP: HOTP with T = ⌊t/30⌋, accept ±1 step
  • Push fatigue, SIM swap, real-time phishing
