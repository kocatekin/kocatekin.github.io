MAC & HMAC: Message Authentication Codes

Tuğberk Kocatekin · Arel University · Interactive lecture notes (works offline)

1Why hashes are not enough

In the hash lecture, Alice sent a message together with its hash, and Bob recomputed the hash to check it. That protects against accidental changes, such as transmission errors or corrupted downloads.

But a hash function has no secret. Anyone can compute it. An attacker in the middle (Mallory) can change the message and simply recompute the hash. Bob's check still passes.

The missing ingredient: a secret keyTo prove that a message came from Alice and was not modified, the "fingerprint" must be something only Alice (and Bob) can compute. That is exactly what a Message Authentication Code is.

2What is a MAC?

A Message Authentication Code (MAC) is a short tag computed from a message and a secret key:

tag = MAC(K, m)

Alice and Bob share the key K in advance (it is symmetric cryptography). Alice sends m ‖ tag. Bob recomputes MAC(K, m) and accepts only if it equals the received tag.

What a MAC gives you

  • Integrity: any change to the message is detected.
  • Data-origin authentication: the message was created by someone who knows K.

What a MAC does not give you

  • Confidentiality: the message itself travels in plaintext. Use encryption for secrecy (§12).
  • Non-repudiation: Bob also knows K, so he could have produced the tag himself. Bob cannot prove to a judge that Alice sent it. For that you need digital signatures (§5).
  • Freshness: an old valid message can be replayed (§3).

4What makes a MAC secure?

The standard security goal is unforgeability. Imagine a strong attacker who can ask Alice for valid tags on any messages she likes (a chosen-message attack). Even after seeing many (message, tag) pairs, she must not be able to produce a valid tag for any new message. Cryptographers call this existential unforgeability under chosen-message attack (EUF-CMA).

Generic attacks every MAC faces

AttackHowCostDefence
Key searchTry every key until the tags match known pairs≈ 2k for a k-bit keyKeys of ≥ 128 random bits
Tag guessingSend a forged message with a random tag and hopesuccess probability 2−t per try for a t-bit tagTags long enough (≥ 64–128 bits), rate limiting

Tag guessing is online: every try must be sent to Bob, who can notice and block it. That is why short tags (e.g. 64 bits, or even a 6-digit TOTP code) are acceptable in some protocols, while keys must always be long.

Is a MAC like a hash?A good MAC should behave like a pseudorandom function: for someone without the key, the tag looks like random bits. Collision resistance in the hash sense is not required, because the attacker cannot compute tags offline.

6Building a MAC from a hash: naive ideas

We already have fast, well-studied hash functions. Can we just mix the key into the hash? Three obvious attempts:

ConstructionIdeaProblem
H(K ‖ m) secret prefixkey first, then messagebroken by the length-extension attack for MD5, SHA-1 and SHA-256 (§7)
H(m ‖ K) secret suffixmessage first, then keyweak if the attacker finds a collision H(m₁) = H(m₂) offline (no key needed), then a tag for m₁ is also valid for m₂. Security drops to collision resistance.
H(K ‖ m ‖ K) envelopekey on both sidesad hoc better, but has had published weaknesses and no clean proof

Why secret-prefix fails: the Merkle–Damgård structure

MD5, SHA-1 and SHA-2 process the message in fixed-size blocks (64 bytes for SHA-256). A compression function f mixes each block into a running internal state. The final digest is the final internal state.

Because the tag is the internal state, an attacker can load it back into SHA-256 and keep hashing more blocks, without ever knowing K. The result is a valid tag for K ‖ m ‖ padding ‖ extra.

What happened?The forged request contains the original message, then the padding bytes SHA-256 added internally, then the attacker's data. Many servers keep the last value of a repeated parameter, so role=admin wins. This exact flaw was found in the Flickr API in 2009 (MD5(secret ‖ args)).

Hash functions that do not output their full internal state are immune: SHA-3, BLAKE2/3, and truncated SHA-2 variants such as SHA-384 and SHA-512/256. But the clean general fix is HMAC.

8HMAC

HMAC (Hash-based MAC) was designed by Bellare, Canetti and Krawczyk (1996), standardised in RFC 2104 (1997) and FIPS 198-1. It turns any iterated hash function H into a secure MAC: HMAC-SHA256, HMAC-SHA1, HMAC-SHA512, …

HMAC(K, m) = H( (K' ⊕ opad) ‖ H( (K' ⊕ ipad) ‖ m ) )

K'   = K padded with zeros to the block size B   (if K is longer than B, K' = H(K) padded)
ipad = 0x36 repeated B times       ("inner pad")
opad = 0x5c repeated B times       ("outer pad")
B    = 64 bytes for SHA-1/SHA-256, 128 bytes for SHA-512

In words: hash the message with one key-derived prefix (the inner hash), then hash that result again with a different key-derived prefix (the outer hash).

9Why HMAC is secure

  • The outer hash hides the inner state. The tag is a hash of the inner hash, keyed again with K' ⊕ opad. Length extension on the tag would only extend the outer hash, which the server never computes that way. Try the HMAC button in §7: every attempt fails.
  • Two different keys. ipad and opad differ in many bits, so the inner and outer hashes are keyed with effectively independent keys.
  • The key is processed first. The first block of each hash is entirely key-derived, so the compression function starts from a secret state, effectively a secret IV.
  • Security proof. HMAC is provably a secure PRF/MAC as long as the hash's compression function behaves like a PRF. Notably, this does not require collision resistance.
HMAC-MD5 and HMAC-SHA1?Because HMAC does not rely on collision resistance, MD5's and SHA-1's broken collision resistance does not directly break HMAC-MD5 or HMAC-SHA1, and no practical forgery is known for HMAC-SHA1. Still, for new designs use HMAC-SHA256 or stronger; avoid MD5 entirely.

Keys and tag length

  • Use a random key at least as long as the hash output (32 bytes for HMAC-SHA256). Do not use a human password directly; derive keys with a KDF.
  • Keys longer than the block size are first hashed, so a 200-byte key gives no more security than a 32-byte one.
  • Tags may be truncated (e.g. HMAC-SHA256-128). RFC 2104 recommends keeping at least half the hash output and at least 80 bits.

10Verifying tags: timing attacks

Computing the tag correctly is only half the job. A typical string comparison stops at the first different byte:

def naive_equal(a, b):        # what  ==  /  memcmp  do internally
    for x, y in zip(a, b):
        if x != y:
            return False      # early exit → leaks WHERE the first mismatch is
    return True

A tag whose first character is correct is rejected a tiny bit later. By measuring response times, an attacker can recover a valid tag for her forged message one character at a time, needing about 16 × length guesses instead of 16length. This really happened, e.g. against the Xbox 360 boot loader's HMAC check.

The fix is a constant-time comparison that always looks at every byte, e.g. hmac.compare_digest in Python, crypto.timingSafeEqual in Node.js, MessageDigest.isEqual in Java, CRYPTO_memcmp in OpenSSL.

def constant_time_equal(a, b):
    if len(a) != len(b):
        return False
    diff = 0
    for x, y in zip(a, b):
        diff |= x ^ y          # no early exit
    return diff == 0

Encryption + MAC: which order?

OrderSentVerdict
Encrypt-then-MACC = Enc(K₁, m), tag = MAC(K₂, C)recommended reject forged ciphertexts before decrypting
MAC-then-encryptEnc(K₁, m ‖ MAC(K₂, m))risky led to padding-oracle attacks in SSL/TLS (e.g. Lucky 13, POODLE)
Encrypt-and-MACEnc(K₁, m), MAC(K₂, m)risky the tag of the plaintext can leak information (SSH historically)

Today the usual answer is AEAD (Authenticated Encryption with Associated Data): AES-GCM or ChaCha20-Poly1305 encrypt and authenticate in one correct, standard step. Use separate keys for encryption and MAC if you combine them yourself.

13Common pitfalls

  • Using a plain hash (SHA-256(m)) as if it authenticated the sender
  • Inventing your own construction like SHA-256(key ‖ msg) (length extension)
  • Comparing tags with == instead of a constant-time function
  • No sequence number / timestamp → replay attacks
  • Short, guessable or hard-coded keys (or a password used directly as the key)
  • Reusing the same key for encryption and for the MAC
  • MACing only part of the message (e.g. forgetting headers or the IV)
  • Use HMAC-SHA256 (or an AEAD), random 256-bit keys, constant-time verification, and authenticate a counter/nonce with every message

Summary

  • A MAC is a keyed checksum: tag = MAC(K, m). It gives integrity and authentication, but not confidentiality or non-repudiation.
  • Plain hashes can be recomputed by an attacker; MACs cannot without the key.
  • H(K ‖ m) is broken by length extension for Merkle–Damgård hashes (MD5, SHA-1, SHA-2).
  • HMAC = H((K'⊕opad) ‖ H((K'⊕ipad) ‖ m)); the outer hash blocks length extension, and security does not need collision resistance.
  • Verify tags in constant time and protect against replay with counters or timestamps.
  • HMAC is everywhere: TLS/HKDF, JWT, API signing, cookies, PBKDF2, TOTP.
