CHF: Cryptographic Hash Functions

Tuğberk Kocatekin · Arel University · Interactive lecture notes (works offline)

1Introduction

A hash function takes a variable-sized input message and produces a fixed-size output. The output is called the hashcode, hash value or message digest.

You can think of the digest as a fixed-size fingerprint of a message. For a good cryptographic hash, two different messages having the same fingerprint is so unlikely that, in practice, we treat it as unique.

Careful with "unique"Digests are not mathematically unique: there are infinitely many inputs but only 2n outputs, so collisions must exist (see §8). What we rely on is that nobody can find one.

Paste a whole paragraph or a single letter. The input length changes; the digest length never does.

2Properties & the avalanche effect

  • The size of the output is fixed.
  • It is deterministic: the same input always gives the same digest.
  • Any change in the input results in a very different output. This is the avalanche effect: flipping a single input bit should flip about half of the output bits, unpredictably.

Totally different! This is very good: an attacker cannot make a "small" change to a message and get a predictably similar hash.

3One-way functions

Hash functions are one-way functions: computing the digest from the input is easy, but recovering the input from the digest is infeasible. There is no inverse function.

Note that "one-way" does not mean "impossible to guess". If the set of possible inputs is small (a PIN, a coin flip, a common password), an attacker can simply hash every candidate. We return to this in §10–§12.

5Where do we use them?

Data integrity & file verificationDetect that data was altered during storage or transmission. Download pages publish a file's hash so you can check it before opening.
Password storageStore a (salted, slow) hash instead of the plaintext password.
Digital signaturesThe message is hashed first, and the digest is signed with the owner's private key.
BlockchainsEach block contains the hash of the previous block, creating a tamper-evident ledger.
MACsCombine a hash with a secret key (e.g. HMAC) to authenticate messages.
GitEvery object (commit, tree, file) is identified by its SHA-1 hash. Newer Git also supports SHA-256.
Commitment schemesCommit to a value now, reveal it later, and prove you did not change it.

Important limitationA plain hash only detects accidental changes (or changes when the hash travels over a separate trusted channel, like a download page over HTTPS). An active attacker who can change the message can simply recompute the hash. To authenticate the sender we need a secret: a MAC such as HMAC(key, message), or a digital signature.

The tamper detection comes from the avalanche effect and second-preimage resistance: any change to the message changes the hash, and the attacker cannot find a different message with the same hash.

7Cryptographically secure hash functions

A hash function is called cryptographically secure if the following problems are computationally infeasible:

PropertyAttacker is given……and must findGeneric cost (n-bit hash)
Preimage resistance (one-way)a digest zany x with h(x) = z≈ 2n
Second-preimage resistance (weak collision resistance)a message m1m2 ≠ m1 with h(m2) = h(m1)≈ 2n
Collision resistance (strong collision resistance)nothingany pair m1 ≠ m2 with h(m1) = h(m2)≈ 2n/2 (birthday bound, §9)

Collision resistance is the easiest property to attack because the attacker gets to choose both messages. That is why a 256-bit hash gives about 128 bits of collision security.

Still, collisions definitely exist, by the pigeonhole principle.

8Pigeonhole principle & collisions

There are (practically) infinitely many inputs but only a fixed number of outputs. With n output bits there are 2n possible digests: a lot, but not infinite. So some different messages must share a digest.

Toy hash: keep only the first 3 bits of SHA-256 → 8 holes

Notice that with only 8 holes you usually get a collision after about 4 or 5 messages, long before all 8 holes are full. That surprise has a name: the birthday paradox.

9The birthday paradox

Question: how many people must be in a room for there to be a better than 50% chance that two of them share a birthday?

Most people guess around 183 (half of 365). The real answer is just 23. It is not a true paradox, only a result that defeats our intuition.

Why so few? Count the pairs

We are not asking whether someone matches one particular person. Any pair is allowed to match, and the number of pairs grows quadratically:

pairs among k people = k(k−1)/2
k = 23  →  23·22/2 = 253 pairs, each matching with probability 1/365

253 chances, each with probability 1/365, add up to a lot. Compare this with the question "does anyone share my birthday?". There, only k pairs involve you, so you need about 253 other people for a 50% chance.

The math

It is easier to compute the probability that there is no match, and subtract it from 1. With N possible values (N = 365 days) and k people, each new person must avoid all earlier ones:

P(no match) = (N/N)·((N−1)/N)·((N−2)/N)···((N−k+1)/N)
            = ∏ (1 − i/N)   for i = 0 … k−1

using 1 − x ≈ e^(−x):
P(no match) ≈ e^(−k(k−1)/(2N))
P(match)    ≈ 1 − e^(−k²/(2N))

Setting P(match) = ½ and solving for k:

k ≈ √(2·ln2·N) ≈ 1.18·√N        (N = 365 → k ≈ 22.5 → 23 people)
expected people until first match ≈ √(πN/2) + 1 ≈ 24.6
The key takeawayCollisions start to appear after about √N samples, not N. Square root is a huge reduction: √(2n) = 2n/2.
Simulation: fill a room until two birthdays collide

From birthdays to hash functions

Replace "365 days" with "2n possible digests". An attacker who simply hashes random messages and stores the results will find two that collide after about 2n/2 hashes. This generic birthday attack works against every hash function, however well designed.

Each 8 extra bits multiplies the number of outputs by 256 but the work only by 16. That is the square root at work.

  • Rule of thumb: an n-bit hash gives only n/2 bits of collision security. For 128-bit security you need a digest of at least 256 bits. This is why 128-bit MD5 was too short even before it was broken.
  • Yuval's birthday attack on signatures: Mallory writes many harmless variations of a fair contract (extra spaces, synonyms, commas) and many variations of a fraudulent one. With about 2n/2 of each, a fair version and a fraudulent version will likely have the same hash. Alice signs the fair one, and the signature is equally valid for the fraudulent one.
  • Memory: a naïve birthday attack stores every hash. Smarter variants (Pollard's rho, distinguished points) find collisions with almost no memory, so the 2n/2 bound is the real limit.

10Commitment schemes

Hashing the choice alone is not enough"heads" and "tails" are only two values; anyone can hash both and read the commitment. A secure commitment is h(choice ‖ random nonce). The same applies to "guess which number I have in mind".

11Password storage & salting

Storing passwords in plaintext is wrong and not secure. We store a hash instead, so if the database is stolen, the attacker does not directly see the passwords. Is this enough? What can go wrong?

What does the stolen database look like?

  • Problem 1: identical passwords produce identical hashes, so one cracked hash reveals everyone using it.
  • Problem 2: attackers can precompute hashes of common passwords once and reuse them against every database (lookup / rainbow tables).
  • Salting: generate a random, unique salt per user, store salt, h(salt ‖ password). The salt is not secret; it just forces the attacker to attack each user separately and makes precomputed tables useless.
  • Slow hashing: SHA-256 is designed to be fast, which helps attackers try billions of guesses per second. Real systems use deliberately slow, salted password-hashing functions: Argon2, bcrypt, scrypt or PBKDF2.

12Attacks: brute force, dictionaries, rainbow tables

We cannot invert a hash, so attackers guess: hash a candidate and compare it with the target.

  • Brute force: try every possible string (a, b, …, aa, ab, …). Guaranteed but exponentially slow.
  • Dictionary attack: try only likely passwords from a wordlist such as rockyou.txt. Tools like John the Ripper and hashcat also apply rules (capitalise, append digits, l33t-speak…).
  • Precomputed tables: hash a huge wordlist once, store hash → password, and look targets up instantly. A rainbow table is a space-efficient version: it stores chains built from alternating hash and "reduction" functions, trading lookup time for much less storage.

Won a public NIST competition in 2012, standardised in 2015 (FIPS 202). Different "sponge" internal structure.

Notes

  • MD5: 128-bit digests, broken multiple times. hashlib.md5(b"crypto").hexdigest()
  • SHA-1: 160-bit digests, not secure anymore (collisions found). hashlib.sha1(b"crypto").hexdigest()
  • SHA-2: SHA-256 and SHA-512 are the two core functions; they differ in word size (32 vs 64-bit), so SHA-512 is often faster on 64-bit processors.
  • SHA-3: supports the same output lengths as SHA-2 but uses the sponge construction, which makes it immune to length-extension attacks (a weakness of MD5/SHA-1/SHA-2 when misused as h(key ‖ message)). It is very efficient in hardware and somewhat slower in software. That slowness is a side effect, not a security feature.

Summary

  • A CHF maps any input to a fixed-size digest, deterministically and fast.
  • Security = preimage, second-preimage and collision resistance (collisions exist, but can't be found).
  • Birthday paradox: collisions appear after about √N tries, so an n-bit hash gives only n/2 bits of collision security.
  • Avalanche effect: a tiny input change flips ~50% of the output bits.
  • A plain hash gives integrity against accidents; authentication needs a key (HMAC) or a signature.
  • Low-entropy inputs (passwords, coin flips) need salts/nonces; passwords also need slow hashing.
  • Use SHA-256/SHA-512/SHA-3 for security; avoid MD5 and SHA-1.
