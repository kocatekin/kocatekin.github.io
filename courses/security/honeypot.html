    Honeypots & Honeytokens

    Deception as a defence: instead of only keeping attackers out, we build things that look valuable, let attackers touch them, and learn from every move they make.

    How to use this page: read each section, try the interactive parts, answer the check questions, write your own notes in the blue boxes and tick “I understand this section”.
    Section 1

    What is a honeypot?

    Honeypot — a system or resource that is deliberately made to look vulnerable or interesting to attackers, so that we can attract, detect, study and sometimes deflect them. It has no production purpose, so any interaction with it is suspicious by definition.

    A honeypot is not about protecting the honeypot itself. Its value comes from being probed, attacked and even compromised — while we watch. It looks real, but it is isolated from real systems, so nothing an attacker does there can reach production.

    🧲 AttractLook like a juicy target: open ports, old software, “interesting” files.
    🚨 DetectNo legitimate user should ever touch it — every hit is an alert.
    🔬 StudyRecord commands, tools, malware and timing to learn how attackers work.
    ↪ DeflectWaste the attacker’s time and effort on a fake target.

    A short history

    1986–89 — Clifford Stoll (Lawrence Berkeley Lab) tracks a hacker by planting fake “SDInet” military files to keep him connected long enough to trace — an early honeytoken. Told in The Cuckoo’s Egg.
    1991 — Bill Cheswick (AT&T) publishes An Evening with Berferd: he lures an intruder into a jailed, fake environment and studies him for months.
    1997 — Fred Cohen releases the Deception Toolkit, one of the first freely available honeypot tools.
    1999 — Lance Spitzner founds the Honeynet Project; honeypots become a research field.
    2003 — The term honeytoken appears (Augusto Paes de Barros) and is popularised by Spitzner.
    2005 — Anagnostakis et al. introduce shadow honeypots (USENIX Security).
    Today — “Deception technology” products, Canarytokens, cloud honeypots and LLM-driven honeypots.

    Why does a honeypot produce very few false positives?
    A honeypot needs no “clever” detection: since nothing legitimate uses it, the mere fact that someone connected is the signal.
    Section 2

    Low, medium & high interaction

    Honeypots are classified by how much of a real system the attacker can interact with. More interaction gives us more information — but also more risk and more work.

    • Low interaction — emulated services with a small subset of functionality. Instead of a whole server you only implement e.g. a login banner and a password prompt. Cheap and safe; attackers detect it quickly.
    • Medium interaction — a richer emulation: a fake shell with a fake file system, fake command output, downloads are captured but never executed. (Example: Cowrie SSH/Telnet honeypot.)
    • High interaction — a real operating system with real services. The attacker interacts with it just like any machine. Maximum information, maximum risk: if containment fails, the attacker can use it to attack others.

    What do we collect?

    🌐 IP addressesSource IPs, ASNs, geolocation, scanning ranges.
    🧭 Attack patternsOrder of commands, timing, which ports and paths are probed.
    🦠 Malware samplesFiles the attacker downloads or uploads (hashes, binaries, scripts).
    🛠 Exploit techniquesPayloads, credentials tried, vulnerabilities targeted.

    Common examples: fake web servers, SSH/Telnet honeypots, database honeypots (MySQL, MongoDB, Redis, Elasticsearch), industrial control system honeypots, and exposed fake AI/LLM endpoints.

    Check yourself
    You want to capture the full post-exploitation behaviour of skilled attackers. Which type do you choose, and what is the main cost?
    High interaction gives you the most realistic behaviour but a real OS can really be abused, so data control (outbound limits, isolation) is essential.
    Section 3

    What attackers do inside a honeypot

    Studies of SSH honeypots show a fairly consistent sequence of behaviour, although it differs between bots, script kiddies and experienced attackers. Bots usually run one preset script within seconds: download a payload from an IP address, run it, leave. Humans explore.

    Section 4

    Building a believable honeypot

    Attackers test whether a system is real, just as we test whether they are malicious. A honeypot that is easy to fingerprint collects only bot traffic, and skilled attackers simply leave (or feed you false data). Building a good honeypot therefore starts with research: learn how attackers work and what a real system of that kind looks like.

    Realism checklist — SSH honeypot on Linux

    📂 File systemls returns proper, lived-in results; realistic files under /etc, /var/log, home directories with history.
    ⏱ TimingCommands take realistic time; downloads are not instant; the clock and uptime make sense.
    🖥 HardwareBelievable CPU, memory, disk (nproc, free -m, /proc/cpuinfo).
    🔖 Defaults changedHostnames, banners, kernel versions and users must not be the tool’s defaults — attackers keep lists of known honeypot fingerprints.
    🧩 ConsistencyIf echo hi > a.txt then cat a.txt must show hi. State must persist.
    🍯 BaitPlant fake but plausible data (configs, DB dumps, credentials) — i.e. honeytokens — to see what attackers go after.
    LLMs as honeypot enginesLarge language models are good at producing realistic, context-aware responses (shell output, HTTP/REST API responses) on the fly, which makes medium-interaction honeypots far more convincing. Recent research, e.g. work by Anıl Sezgin on using LLMs to generate REST API honeypots, and evaluation frameworks for LLM-powered HTTP honeypots, explores this direction. Weaknesses to discuss: latency, inconsistent answers between commands, cost, and prompt-injection by the attacker.

    Section 5

    Honeytokens

    Honeytoken — a decoy piece of data (a fake document, credential, API key, database row or email address) that has no legitimate use in your system. When anyone reads, uses or sends it, an alert is raised.

    A honeytoken is a tripwire, not a trap system. It does not engage the attacker; it silently tells you that someone touched something nobody should touch — and often where the data ended up.

    Common types

    🔑 CredentialsFake username/password, API token or cloud access key. Any login attempt with them = alert.
    📄 DocumentsDummy files such as passwords.xlsx or financial_report.docx that “phone home” when opened.
    🗄 Database recordsFake rows (e.g. a customer that does not exist). If that row appears in a query, an export or a leak, you know.
    ✉ Email addressesAn address used nowhere legitimate. If it ever receives mail, your list was stolen or sold.
    🔗 URLs / DNS namesA unique link or hostname; resolving it reveals the visitor’s IP.
    ☁ Cloud keysFake cloud keys left in code or config; every API call with them is logged by the provider and alerts you.
    Deliberately leaked secretsSometimes you will see screenshots or public code repositories that show API keys or passwords in plain sight. Some of these are planted on purpose: the keys may even “work”, but they lead only to monitored decoys. Lesson for attackers — and for us: a leaked secret is not necessarily a real secret.

    Why use them?

    Early detectionReal users never touch decoys, so interaction is a strong sign of unauthorised access — often before real damage.
    Low false positivesNo legitimate purpose → alerts are almost always genuine.
    Cost-effectiveLightweight, no extra infrastructure, easy to scatter across many systems.
    Threat intelligenceReveal attacker IP/location, tools, and how they move through the network (lateral movement).

    How to deploy them well

    1. Place them where an attacker looks — sensitive directories, admin desktops, config files, password managers, code repositories.
    2. Make them look real — realistic names, sizes, dates and content. honeytoken.txt catches no one.
    3. Connect them to monitoring — IDS/SIEM rules or a canary service, so access becomes an alert someone actually sees.
    4. Rotate and update — attackers also learn; old, never-changing decoys get recognised.
    5. Test regularly — trigger your own tokens. You think everything is in place, but does the alert really arrive?
    6. Tell the right people — the SOC must know they exist; ordinary staff should not, or they may open them out of curiosity.
    Check yourself
    A fake customer record “Mehmet Yılmaz, mehmet.y.7731@…” exists only in your CRM database. One day that address receives spam. What does this most likely mean?
    The address existed nowhere else, so the only way to know it is to have the database contents — a strong leak indicator.

    Section 7

    Honeynets & honeyfarms

    A honeynet is a network of honeypots: each node is a honeypot, but together they mimic a complete environment — workstations, a file server, a database, maybe a domain controller. Attackers who get in can scan, pivot and move laterally, and we see all of it.

    • Used to detect, deflect and analyse attacks at network level.
    • Gives high visibility into attacker behaviour — especially lateral movement, which a single honeypot cannot show.
    • Few false positives (still no legitimate users).
    • Can reveal zero-day exploits: when an unknown technique works, we have the full traffic and the compromised host.

    A classic honeynet sits behind a honeywall, a gateway that provides three functions:

    Data controlLimit outbound traffic so the compromised honeynet cannot attack others (rate limits, blocking known exploit traffic).
    Data captureRecord everything: packets, keystrokes, files — without the attacker noticing.
    Data analysisTurn raw logs into knowledge: who, how, what was the goal.

    Honeyfarm

    A honeyfarm is the large-scale, centrally managed version: many honeypots and honeynets, often in many locations or cloud regions, all reporting to one place.     Section 8

    Shadow honeypots

    A shadow honeypot is normally not active. It is a copy (or instrumented version) of the real application that is used only when an anomaly detector or IDS flags traffic as suspicious. That traffic is diverted to the shadow in real time; the attacker carries on as if everything were normal, while everything is logged and later analysed to improve defences.

    Benefit: an IDS alone must choose between blocking (risking false positives that hurt real users) and allowing (risking an attack). A shadow honeypot sidesteps this: suspicious-but-uncertain requests get a realistic answer from a safe copy.

    Dynamic deploymentActivated only when needed, reducing exposure.
    Realistic interactionRuns the real application logic (or a clone), so it is highly convincing.
    Integrated monitoringUsually connected to analytics and threat-intelligence platforms.

    Example use cases

    • Web applications — a suspicious HTTP request triggers a shadow copy of the full backend that answers instead of the real one.
    • Cloud environments — shadow honeypots spin up as containers or VMs to capture anomalous traffic in dynamic infrastructure.
    • Zero-day research — novel attacks that evade signatures still look anomalous; observing them in the shadow reveals the new technique.
    Check yourself
    A user searches for “O’Brien” and the IDS flags the apostrophe as possible SQL injection. With a shadow honeypot, what happens?
    That is the point of shadowing: uncertain traffic is handled safely instead of being blocked. (In the original design, the shadow’s state changes are rolled back if an attack is confirmed, and committed if the request turns out benign.)
    Section 9

    Placement, risks & ethics

    Where do we put them?

    Internet-facingOutside or in the DMZ. Receives huge amounts of scanning and bot traffic — great for research, noisy for alerts.
    Internal networkNext to real servers. Should never be touched; any hit means someone is already inside (or an insider is snooping).
    Inside dataHoneytokens in databases, file shares, code repos, cloud accounts and email lists.

    Risks and limitations

    • Abuse as a launch pad — a compromised high-interaction honeypot can attack others. Strict outbound control is mandatory.
    • Fingerprinting — skilled attackers detect honeypots and avoid them, or feed false information.
    • Narrow field of view — a honeypot only sees attacks aimed at itself; it does not replace firewalls, IDS, patching or EDR.
    • Maintenance — honeypots must be updated, monitored and tested, or they become noise (or a liability).

    Legal & ethical questions (for discussion)

    • Privacy / data protection — honeypots record IP addresses and possibly personal data. Under KVKK (Turkey) or GDPR (EU), you still need a lawful basis, retention limits and security for these logs.
    • Liability — if your honeypot is used to harm a third party, you may be responsible.
    • Entrapment — usually discussed but rarely relevant for private defenders: honeypots do not induce a crime, they only observe one. Still, rules differ by country; ask a lawyer before a real deployment.
    • Hack-back — using honeypot data to attack the attacker is illegal in most jurisdictions. Report, do not retaliate.

    Real-world usage

    Military / governmentHigh-interaction honeypots and honeynets to distract attackers and make them waste time and resources, and to study state-level threats.
    EnterpriseInternal honeypots and honeytokens to detect intrusions and lateral movement early, and to catch insiders accessing data they are not authorised to see.
    Academic / researchCapturing malware payloads, studying ransomware behaviour, tracking botnet propagation, publishing datasets.
    Check yourself
    Your internal honeypot (never announced to anyone) logs an SMB login attempt from an HR laptop. What is the best first reaction?
    An internal decoy has no legitimate users. A hit is either malware moving laterally or a person looking where they should not — both need investigation.
    Section 10 · Lab

    Lab: building a small web honeypot

    In the lab we build a deliberately “vulnerable-looking” website that logs everything. It never executes anything the attacker sends; it only pretends. Below is a minimal starting point using only Python’s standard library.

    Lab safety rulesRun it on 127.0.0.1 or an isolated lab network/VM only. Do not expose it to the internet without your instructor’s approval and proper isolation. Never run real vulnerable software on a university or personal network.
    honeyweb.py
    # honeyweb.py — minimal logging web honeypot (lab use only)
import json, datetime
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import urlparse, parse_qs

LOGIN_PAGE = b"""<html><title>Admin Panel</title><body>
<h2>Site Administration</h2>
<form method=POST action=/admin/login>
 User <input name=user> Pass <input name=pass type=password>
 <button>Login</button></form></body></html>"""
BAIT_PATHS = {"/admin", "/wp-login.php", "/phpmyadmin", "/.env", "/backup.zip"}

def log(event):
    event["time"] = datetime.datetime.utcnow().isoformat() + "Z"
    with open("honey.log", "a") as f:
        f.write(json.dumps(event) + "\n")

class Honey(BaseHTTPRequestHandler):
    server_version = "Apache/2.4.41 (Ubuntu)"   # look like a real server
    sys_version = ""

    def _record(self, body=""):
        u = urlparse(self.path)
        log({"ip": self.client_address[0], "method": self.command,
             "path": u.path, "query": parse_qs(u.query),
             "ua": self.headers.get("User-Agent"), "body": body[:2000],
             "bait": u.path in BAIT_PATHS})

    def do_GET(self):
        self._record()
        if self.path.startswith("/admin") or self.path == "/wp-login.php":
            self._send(200, LOGIN_PAGE)
        elif self.path == "/.env":   # honeytoken: fake secrets
            self._send(200, b"DB_USER=app_admin\nDB_PASS=Spring2025!\nAWS_KEY=AKIAFAKEFAKEFAKE0001\n")
        else:
            self._send(404, b"Not Found")

    def do_POST(self):
        n = int(self.headers.get("Content-Length", 0))
        self._record(self.rfile.read(n).decode(errors="replace"))
        self._send(200, b"Invalid username or password.")   # always fail

    def _send(self, code, body):
        self.send_response(code)
        self.send_header("Content-Type", "text/html")
        self.end_headers(); self.wfile.write(body)

    def log_message(self, *a): pass   # keep the console quiet

if __name__ == "__main__":
    HTTPServer(("127.0.0.1", 8080), Honey).serve_forever()

    Lab tasks

    1. Run the script and visit http://127.0.0.1:8080/admin, /.env and a random path. Open honey.log.
    2. “Attack” it yourself: try SQL-injection-style inputs in the login form, use curl with a fake User-Agent. Find each attempt in the log.
    3. Make it more realistic: add a robots.txt that “hides” /backup.zip, add realistic latency, add more bait pages.
    4. Wire the honeytoken: write a second tiny script that alerts (prints in red, or sends a message) when a request reads /.env.
    5. Analyse: write a short Python script that counts requests per IP and per path, and lists all usernames/passwords tried.
    6. Discuss: how could an attacker tell this is a honeypot? Fix at least two of those clues.
    Project ideaA full web honeypot with realistic pages, an LLM- or template-driven backend, and a data-processing/visualisation pipeline for the collected logs is a strong graduation project topic.
