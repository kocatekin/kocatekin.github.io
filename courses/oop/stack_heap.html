    Stack and Heap

    Where do your variables actually live? Java keeps them in two different places. Once you can picture both, a lot of “weird” Java behaviour stops being weird.

    Student s = new Student("Ayşe", 20);
    the variable: lives on the stack the object: lives on the heap

    1Two places in memory

    When your program runs, Java uses two areas of memory for your data.

    The stack is like a pile of notepads. Every time a method is called, Java puts a fresh page on top of the pile. That page is called a frame, and it holds the method’s local variables and parameters. When the method finishes, its page is torn off and thrown away. Automatic, fast, and small.

    The heap is like a big storage room. Every time you write new, Java puts an object somewhere in that room. Objects don’t belong to any method. They stay as long as somebody can still reach them, even after the method that created them has ended.

    The most important sentence today

    A variable whose type is a class (like Student s) never holds the object itself. It holds an arrow to the object, called a reference. A primitive variable (like int age) holds the value directly.

    Takeaway

    t = s copies the arrow, not the object. After that, changing the object through t is visible through s, because there is only one object. This is also why == on objects asks “same arrow target?”, which you saw with equals().

    3Method calls and frames

    Now watch the stack itself. Each method call gets its own frame. The newest frame sits on top and is the only one running; the frames below it are paused, waiting for it to return.

    • Every call gets a brand-new frame, with its own variables. n in square and x in main are different boxes.
    • Parameters are copies. n got a copy of the value of x.
    • Returning removes the frame (“pops” it). Its local variables are gone for good. That’s why a local variable can’t be used outside its method.

    4Passing objects to methods

    This is the part that confuses almost everyone, and the stack and heap picture makes it simple. Java always passes a copy of the variable into a method. For an int, that’s a copy of the number. For an object variable, that’s a copy of the arrow.

    Two rules

    Changing the object through a parameter (q.x = ...) is visible to the caller. Both arrows point to the same object.

    Reassigning the parameter (q = new ...) is not visible to the caller. You only moved your own copy of the arrow.

    5When the stack runs out

    The stack is small. Usually that doesn’t matter, because frames are removed as soon as methods return. But a method that calls itself (recursion) adds a new frame on every call. If it never stops, the frames pile up until there is no room left.

    Try it: call countdown(4)

    Run it with the base case first. Then remove the base case and run again.

    stack limit
    static void countdown(int n) {
    if (n == 0) return;          // base case: stop here
    countdown(n - 1);
}

    StackOverflowError is an Error, not an Exception. Remember the hierarchy from the exceptions week: Throwable splits into Exception and Error, and Errors are problems you don’t catch, you fix. Here the fix is a base case that stops the recursion.

    6Garbage

    Stack frames clean themselves up. Heap objects don’t; nobody “deletes” an object in Java. Instead, the garbage collector (GC) runs every now and then and frees objects that can no longer be reached. An object is reachable if you can get to it by starting at a variable on the stack and following arrows.

    Memory leaks in Java

    If garbage is collected automatically, can Java still run out of memory? Yes: when you keep arrows to objects you no longer need. A classic example is a list that only ever grows:

    public class Logger {
    private static List<String> history = new ArrayList<>();

    public static void log(String message) {
        history.add(message);    // added forever, never removed
    }
}

    A static field lives as long as the program, and it points to the list, which points to every message ever logged. All of them stay reachable, so the GC is not allowed to free any of them. Run this for days and you get OutOfMemoryError. The GC only removes what is truly unreachable; it can’t know you stopped caring.

    +Cheat sheet

    • Stack: one frame per method call; holds local variables and parameters. A frame disappears when its method returns.
    • Heap: every object and array made with new, with all its fields. Stays while reachable.
    • A primitive variable holds a value. An object variable holds an arrow (reference), or null.
    • b = a copies the arrow. Two variables, one object.
    • Java passes a copy of each argument. Changing the object through a parameter is visible to the caller; reassigning the parameter is not.
    • An object is garbage when no chain of arrows from the stack reaches it. The GC uses mark and sweep: mark everything reachable, delete the rest.
    • Too many frames (usually recursion without a base case) → StackOverflowError. Too many reachable objects → OutOfMemoryError.
