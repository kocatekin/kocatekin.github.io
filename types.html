Core idea What can the compiler guarantee? Most of the rules in this unit follow from that one question.
Chapter 1

Why Types?

Types are not decoration. They give the language information that can be used to reason about operations before or during execution.

Python — dynamic check 
def print_upper(text):
    print(text.upper())

print_upper("hello")  # works
print_upper(42)       # runtime error
When do we discover the problem? When the failing line actually executes.
Java — static check 
static void printUpper(String text) {
    System.out.println(text.toUpperCase());
}

printUpper("hello");  // OK
printUpper(42);       // compile-time error
When do we discover the problem? During compilation, before the program runs.
Typing is how the compiler knows what you are allowed to do with a value.
Class question: What does this example prove?
It does not prove that Java is a “better” language. It shows one benefit of static type information:
  • Types provide information.
  • The compiler can reason using that information.
  • Some invalid operations can be rejected before runtime.

A useful contrast: coercion

JavaScript: "5" + 3  // "53"
Java:       "5" + 3  // "53"
Python:     "5" + 3  // TypeError

This is useful when discussing coercion and strong/weak typing. It is not the same question as static vs dynamic typing.

Why this matters beyond toy examples

Type information helps tools reason about code before a particular execution path happens. In a large codebase, a bad call may sit untouched for weeks. Static checking can eliminate whole classes of mistakes without relying on someone to execute every path manually.

What static typing can catch

  • Passing an incompatible argument to a method.
  • Calling a method not guaranteed by the expression's static type.
  • Returning the wrong type from a method.
  • Many generic collection mistakes.

What it cannot guarantee

  • That an array index is always in range.
  • That a file exists.
  • That a network service is reachable.
  • That business logic is correct.
Important: static typing reduces some categories of runtime failure. It does not prove that the entire program is correct.

Compile-time vs runtime failure

// Compile-time problem
String s = 42;

// Runtime problem
int[] a = {1, 2, 3};
System.out.println(a[10]);
Chapter 2

What Is a Type?

A practical definition for this course:

A type is a set of possible values together with the operations permitted on those values.

Example

Dog dog = new Dog();
dog.bark();

The compiler allows bark() because the static type Dog guarantees that operation.

Type error

A type error occurs when code attempts an operation that the relevant type does not support.

String name = "Alice";
name.bark(); // compile-time error

Types as guarantees

A useful OOP interpretation is that a type is a contract. If an expression has type Animal, client code may rely on the operations guaranteed by Animal, but not on subtype-specific operations.

Animal a = ...;

a.eat();   // legal if Animal guarantees eat()
a.bark();  // not legal unless Animal guarantees bark()

Primitive and reference types

Java has primitive types such as int and boolean, and reference types such as classes, interfaces, arrays, and enum types. Most of the OOP discussion in this unit concerns reference types.

Expression type vs object identity

The type of an expression is not the same idea as the identity of the runtime object. That distinction becomes crucial later when we write Animal a = new Dog().

Chapter 3

The Four Axes

These are separate questions. A language can be static but inferred, dynamic but strong, and so on.

Static vs Dynamic

When are types checked?

  • Static: primarily before execution.
  • Dynamic: validity is checked as the program executes.

Java: static. Python: dynamic.

Strong vs Weak

How freely can one type be treated as another?

int x = 10;
String s = x; // not allowed

Java is generally described as strongly typed. The terminology is less formally standardized than the other axes.

Explicit vs Inferred

Must the programmer write the type?

String name = "Alice";
var dog = new Dog();

Java is mostly explicit, with type inference in places such as var and generic type arguments.

Type inference is not dynamic typing. var x = "hello" still gives x a fixed static type.

Nominal vs Structural

What makes two types compatible: declared identity or shape?

Java is primarily nominally typed.

class Student { String name; }
class Employee { String name; }

Student s = new Employee(); // error

Same shape does not imply compatibility. A declared relationship such as extends or implements matters.

AxisJavaMain question
Static vs DynamicStaticWhen are types checked?
Strong vs WeakGenerally strongHow much implicit coercion is allowed?
Explicit vs InferredMostly explicit + inferenceMust programmers write the type?
Nominal vs StructuralNominalDoes compatibility depend on declared identity or structure?

The axes are independent

Do not treat these as one spectrum. They answer different questions. A language can be statically typed and inferred, or dynamically typed and strongly typed.

Static vs dynamic

This is mainly about when type constraints are enforced. Java performs extensive static checks. Python performs many checks as operations execute.

Strong vs weak

This terminology is fuzzy across books. It is safest to use it to discuss coercion discipline rather than pretend there is one universal formal definition.

Explicit vs inferred

var x = "hello";
x = 42; // still illegal

var asks the compiler to infer the static type. It does not make the variable dynamically typed.

Nominal vs structural

interface Printable {
    void print();
}

class Report {
    public void print() { }
}

In Java, Report is not automatically a Printable; it must explicitly declare implements Printable. In a structurally typed system, having the required shape may be enough.

Chapter 4

Subtyping

What if one type is a special case of another?

S is a subtype of T if a value of type S can be used where a value of type T is expected.
class Animal {
    void eat() {
        System.out.println("eating");
    }
}

class Dog extends Animal {
    void bark() {
        System.out.println("woof");
    }
}

class Cat extends Animal {
    void meow() {
        System.out.println("meow");
    }
}
Animal
↑
Dog
Cat

Dog <: Animal and Cat <: Animal.

Informally: Dog is-an Animal.

Subtype vs subclass

class Dog extends Animal { }
  • Dog is a subclass of Animal.
  • Dog is also a subtype of Animal.

In Java, both extends and implements create subtype relationships.

Upcasting and downcasting

Dog dog = new Dog();
Animal animal = dog;     // upcasting: safe, implicit

Dog again = (Dog) animal; // downcasting: explicit

Upcasting moves to a more general type. Downcasting asks Java to treat a general reference as a more specific type, which may fail at runtime.

Can this compile? 
Animal animal = new Animal();
Dog dog = animal;
No. Not every Animal is a Dog.

Direction matters

If Dog <: Animal, then a Dog can be used where an Animal is expected. The reverse does not follow.

Animal a = new Dog(); // safe
Dog d = new Animal(); // unsafe and illegal

Why upcasting is implicit

A subtype promises at least the supertype's contract, so moving upward loses specificity but not required guarantees.

Why downcasting is different

Animal a = new Dog();
Dog d = (Dog) a; // works here

Animal b = new Cat();
Dog x = (Dog) b; // compiles, ClassCastException at runtime

The explicit cast says: “I, the programmer, assert that the runtime object is compatible with Dog.” Java still checks that assertion at runtime.

instanceof before a cast

if (a instanceof Dog) {
    Dog d = (Dog) a;
    d.bark();
}

Modern Java also supports pattern matching for instanceof:

if (a instanceof Dog d) {
    d.bark();
}
Chapter 5

Substitutability

Subtyping becomes useful because subtype values can substitute for supertype values.

void feed(Animal animal) {
    animal.eat();
}

feed(new Animal());
feed(new Dog());
feed(new Cat());

All three calls are valid because the method depends only on the Animal contract.

Specific parameter

void makeDogEat(Dog dog) {
    dog.eat();
}

Works only with dogs.

General parameter

void feed(Animal animal) {
    animal.eat();
}

Works with Animal and every valid subtype.

Generality vs specificity:
More specific type → more operations visible, less substitution flexibility.
More general type → fewer operations visible, more substitution flexibility.

Substitutability enables polymorphism

class Animal {
    public void speak() {
        System.out.println("Animal sound");
    }
}

class Dog extends Animal {
    @Override
    public void speak() {
        System.out.println("Woof");
    }
}

class Cat extends Animal {
    @Override
    public void speak() {
        System.out.println("Meow");
    }
}

void makeSpeak(Animal animal) {
    animal.speak();
}

makeSpeak(new Dog());
makeSpeak(new Cat());

The method sees an Animal. The runtime behavior depends on the actual object.

Polymorphic collections

Animal[] animals = {
    new Dog(),
    new Cat(),
    new Dog()
};

for (Animal animal : animals) {
    animal.speak();
}

Each element is statically treated as Animal, while runtime objects may be different subtypes.

Program to an abstraction

interface Database {
    void save();
}

void save(Database database) {
    database.save();
}

Now different implementations can substitute for the abstraction:

save(new MySqlDatabase());
save(new PostgreSqlDatabase());

Substitutability is the practical benefit of subtyping

The client should depend on the supertype's contract, not on assumptions about the concrete subtype.

Vehicle example

class Vehicle {
    public void move() { }
}

class Car extends Vehicle {
    public void openTrunk() { }
}

class Bicycle extends Vehicle {
    public void ringBell() { }
}

Vehicle v1 = new Car();
Vehicle v2 = new Bicycle();

v1.move();       // valid
v2.move();       // valid
v1.openTrunk();  // compile-time error
v2.ringBell();   // compile-time error

General vs specific references

Car car = new Car();
Vehicle vehicle = new Car();

The Car reference exposes more operations. The Vehicle reference accepts a wider range of substitutable objects.

Design trade-off: more general types give you more flexibility; more specific types give you more directly accessible operations.
Chapter 6

Behavioral Subtyping & Liskov Substitution Principle

Compiler-valid substitution is not always behaviorally correct substitution.

Type system says 
class Bird {
    public void fly() {
        System.out.println("Flying");
    }
}

class Penguin extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException();
    }
}
Penguin <: Bird is syntactically legal Java.
Behavior says 
Bird bird = new Penguin();
bird.fly();
The code compiles, but normal Bird behavior is broken at runtime.
Objects of a subtype should be usable in place of objects of the supertype without breaking the correctness of the program.

Syntactic vs behavioral substitutability

KindQuestionExample
SyntacticDoes Java's type system allow it?Animal a = new Dog();
BehavioralDoes the subtype preserve the supertype's expected behavior?A subtype should not unexpectedly break normal operations.
 
class Rectangle {
    protected int width;
    protected int height;

    public void setWidth(int width) {
        this.width = width;
    }

    public void setHeight(int height) {
        this.height = height;
    }

    public int area() {
        return width * height;
    }
}
class Square extends Rectangle {
    @Override
    public void setWidth(int width) {
        this.width = width;
        this.height = width;
    }

    @Override
    public void setHeight(int height) {
        this.width = height;
        this.height = height;
    }
}
void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(10);
    System.out.println(r.area());
}

A caller may reasonably expect area 50. A Square subtype can produce 100, changing the expected semantics.

Java checks type compatibility, not full behavioral correctness

The compiler can verify that required methods exist with compatible signatures. It usually cannot prove that a subtype preserves every semantic expectation of the supertype.

Think in terms of promises

A well-designed subtype should not require callers to know “special exceptions” such as “this Bird cannot really fly” if fly() is part of the supertype's normal contract.

Connection to SOLID

LSP later appears as the L in SOLID. Here, the important point is simply that type-correct inheritance can still model the domain badly.

Better Bird modeling

class Bird { }

interface FlyingBird {
    void fly();
}

class Eagle extends Bird implements FlyingBird {
    public void fly() { }
}

class Penguin extends Bird {
    // no fly() contract
}

This separates “being a bird” from “being able to fly.”

Chapter 7

Interfaces and Subtyping

Subtyping is about contracts, not only parent classes.

interface Payable {
    void pay();
}

class Employee implements Payable {
    @Override
    public void pay() {
        System.out.println("Paying employee");
    }
}

class Invoice implements Payable {
    @Override
    public void pay() {
        System.out.println("Paying invoice");
    }
}

Both relationships create subtypes:

Payable p1 = new Employee();
Payable p2 = new Invoice();

Why interfaces are powerful

void processPayment(Payable payable) {
    payable.pay();
}

The caller does not need to know whether the object is an Employee, Invoice, Subscription, or Vendor. It only relies on the Payable contract.

Interfaces are types

An interface is not merely a list of abstract methods. It creates a type that client code can depend on.

Payable p = new Employee();

The important statement is not “Employee has a pay method.” It is “Employee explicitly promises to satisfy the Payable contract.”

Why this matters for design

  • Callers depend on a small, stable abstraction.
  • Implementations can change independently.
  • Testing is easier because alternative implementations can be substituted.
  • Unrelated classes can share one behavioral contract.
Chapter 8

Static Type vs Runtime Type

This is the bridge from subtyping to runtime polymorphism.

Animal a = new Dog();

Static type = Animal
Runtime type = Dog

What may I call?

Determined by the static type.

Animal a = new Dog();

a.speak(); // allowed if Animal has speak()
a.bark();  // compile-time error if Animal has no bark()

Which override runs?

Determined by the runtime object.

Animal a = new Dog();
a.speak();

If Dog overrides speak(), then Dog.speak() executes.

Core rule:
Static type → what operations are available.
Runtime type → which overridden implementation executes.

Dynamic method dispatch

Animal[] animals = {
    new Dog(),
    new Cat()
};

for (Animal a : animals) {
    a.speak();
}

The same call expression a.speak() can invoke different implementations depending on the runtime object.

Predict the result: 
Animal a = new Dog();
a.speak();
a.bark();
a.speak() can compile if Animal declares it; the Dog override runs. a.bark() does not compile if bark() is only declared in Dog.

Separate two questions every time

  1. Compile time: is this method call permitted through the static type?
  2. Runtime: if the method is overridden, which object's implementation executes?
class Animal {
    public void speak() {
        System.out.println("Animal");
    }
}

class Dog extends Animal {
    @Override
    public void speak() {
        System.out.println("Woof");
    }

    public void fetch() { }
}

Animal a = new Dog();

a.speak(); // legal; Dog.speak() executes
a.fetch(); // compile-time error

Method overriding is dynamically dispatched

For ordinary instance methods, Java selects the overridden implementation using the runtime object.

Do not generalize this rule to fields

Fields are not dynamically dispatched like overridden instance methods. This is one reason to teach the rule specifically as method dispatch.

Chapter 9

Generics

Generics allow reusable code without throwing away compile-time type information.

Without generics 
class Box {
    private Object value;

    public void set(Object value) {
        this.value = value;
    }

    public Object get() {
        return value;
    }
}
Box box = new Box();
box.set(42);

String text = (String) box.get();
// compiles, may fail at runtime
With generics 
class Box<T> {
    private T value;

    public void set(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}
Box<String> box = new Box<>();
box.set(42); // compile-time error

Type parameter vs type argument

class Box<T> { ... }     // T = type parameter

Box<String> textBox;      // String = type argument

Bounded type parameters

class Calculator<T extends Number> {
    ...
}

Valid examples include Integer, Double, and Float.

When a generic bound is an interface, Java still uses extends:

<T extends Comparable<T>>

Multiple bounds:

<T extends Animal & Comparable<T>>

Generics preserve relationships between types

Using Object makes code general by discarding information. Generics make code general while keeping useful type information.

Generic methods

static <T> T first(List<T> list) {
    return list.get(0);
}

The same type parameter connects the input element type to the return type.

Multiple type parameters

class Pair<K, V> {
    private K key;
    private V value;
}

Common naming conventions

T = Type, E = Element, K = Key, V = Value, R = Result.

Raw types

List list = new ArrayList(); // raw type: avoid in new code

Raw types exist mainly for backward compatibility and weaken generic type checking.

Type erasure

Java generics are implemented primarily through type erasure. Generic type arguments are mainly compile-time information, which explains restrictions such as:

if (x instanceof List<String>) { } // illegal

if (x instanceof List<?>) { }      // legal

Primitives are not generic type arguments

List<int>      // illegal
List<Integer>  // correct
Chapter 10

Variance and Wildcards

Ordinary subtyping does not automatically carry through generic containers.

Java generics are invariant by default

Dog <: Animal

does not imply:

List<Dog> <: List<Animal>

Interactive: why not?

Start with step 1.

Wildcards

? means some type whose exact identity is not known here.

List<?>

This is a list of some unknown element type.

Upper-bounded wildcard

? extends Animal

A list of some unknown type that is Animal or a subtype.

List<? extends Animal> animals = dogs;
Safe to read elements as Animal.
Not safe to add Dog, Cat, or general Animal because the exact subtype is unknown.
Lower-bounded wildcard

? super Dog

A list of Dog or some supertype of Dog.

List<? super Dog> destination = animals;
Safe to add a Dog.
Reading is only guaranteed as Object.

Compatibility visualizer

List<Object>
List<Animal>
List<Dog>
List<Cat>
List<String>
List<Poodle>

PECS

Producer Extends, Consumer Super

Producer

List<? extends Animal>

If the collection mainly produces values for you to read.

Consumer

List<? super Dog>

If the collection mainly consumes values that you write into it.

Read/write summary

TypeSafe read typeWhat can be safely added?
List<Animal>AnimalAnimal, Dog, Cat, ...
List<Dog>DogDog (and Dog subtypes)
List<? extends Animal>AnimalEssentially nothing except null
List<? super Dog>ObjectDog (and Dog subtypes)
List<?>ObjectEssentially nothing except null

Type-safety playground

Choose a declared type and an operation.

Three variance ideas

Invariant

Dog <: Animal gives no subtype relationship between List<Dog> and List<Animal>.

Covariant use

List<? extends Animal> accepts lists of Animal subtypes. This is useful when values flow out of the structure.

Contravariant use

List<? super Dog> accepts lists of Dog supertypes. This is useful when Dog values flow into the structure.

Why ? extends cannot accept a Dog insertion

List<? extends Animal> x = ...;

The real object might be List<Cat>. Adding a Dog would violate that hidden exact type.

Why ? super Dog reads only as Object

List<? super Dog> x = ...;

The real object might be List<Animal> or List<Object>, which may already contain non-Dog values.

Copy pattern

static <T> void copy(
        List<? extends T> source,
        List<? super T> destination) {

    for (T item : source) {
        destination.add(item);
    }
}

The source produces T; the destination consumes T. This is PECS in one method.

Arrays are different

Dog[] dogs = new Dog[10];
Animal[] animals = dogs;   // allowed
animals[0] = new Cat();    // runtime ArrayStoreException

Java arrays are covariant, so some errors move to runtime. Generics are stricter and reject the analogous assignment at compile time.

Chapter 11

Duck Typing

Duck typing focuses on what an object can do at runtime, rather than requiring an explicit declared relationship.

“If it walks like a duck and quacks like a duck, treat it like a duck.”
Python 
class Dog:
    def speak(self):
        print("Woof")

class Robot:
    def speak(self):
        print("Beep")

def make_speak(x):
    x.speak()

make_speak(Dog())
make_speak(Robot())

Dog and Robot need no common superclass or declared interface. The function simply assumes that the object supports speak().

Java 
interface Speakable {
    void speak();
}

class Dog implements Speakable {
    public void speak() {
        System.out.println("Woof");
    }
}

class Robot implements Speakable {
    public void speak() {
        System.out.println("Beep");
    }
}

Java normally asks for an explicit nominal relationship such as implements Speakable.

Duck typing vs structural typing

These ideas are related but not identical.

  • Duck typing is usually a runtime style: if an object supports the needed operations, use it.
  • Structural typing is a type-system rule: compatibility can be based on the members a type has rather than its declared name.

Python is famous for duck typing. TypeScript is a common example of structural typing.

Why duck typing is useful

  • Low ceremony.
  • Flexible code that works with unrelated classes.
  • Easy adaptation to new objects that provide the expected behavior.

Trade-off

If an object does not provide the expected operation, the problem may be discovered only when that code path runs.

make_speak(42)
# AttributeError at runtime
Connection to the whole lecture: Java usually wants the compiler to know the contract in advance. Duck-typed code is more willing to discover the contract through actual runtime behavior.

Duck typing is behavior-oriented

A duck-typed function does not require an explicit inheritance or interface declaration. It simply uses the operations it needs.

def make_speak(x):
    x.speak()

Any object that successfully supports speak() can participate.

Relation to nominal typing

Java's normal style is nominal: a class explicitly declares that it implements an interface. Python commonly relies on behavior at runtime instead.

Relation to structural typing

Structural typing and duck typing can look similar because both focus on available members. The difference is that structural typing is usually enforced by a type checker, while duck typing is commonly a runtime programming style.

Python can also use static typing tools

Python type annotations and static analysis tools can add compile-time-like feedback to Python projects, but Python's runtime semantics remain dynamic.

Design lesson

The broader idea is to depend on the behavior you actually need. Java often expresses that need through a small interface; duck-typed languages often express it implicitly.

Final mental model

  • Types describe values and allowed operations.
  • Subtyping describes safe replacement relationships between types.
  • Static type controls what the compiler permits you to call.
  • Runtime type controls which overridden method implementation runs.
  • Generics preserve type information in reusable abstractions.
  • Variance controls how subtype relationships interact with generic types.
  • Duck typing focuses on available behavior rather than an explicit declared relationship.

How to reason through exam-style questions

  1. Write down the static type of every reference.
  2. Write down the runtime type of each object if known.
  3. For a method call, first ask whether the static type exposes the method.
  4. If it compiles and the method is overridden, determine which runtime implementation executes.
  5. For generic types, do not assume subtype relationships are preserved.
  6. For wildcards, ask whether the collection is primarily producing or consuming values.
